# MASTER BUILD PROMPT  
## Gathering of the Fallen — LIVE Music Submission & Queue System

You are building a real, production-ready web application for the music project **Gathering of the Fallen**.

The attached/reference interface images are the visual blueprint for this project. Study ALL provided reference images carefully before implementing anything.

Do not treat the screenshots as random inspiration. They represent the intended visual language, information hierarchy, user flow, admin workflow, LIVE workflow, and overall brand identity.

---

# 1. PRIMARY GOAL

Build an extremely simple self-service music submission and LIVE playback system.

The fundamental rule is:

**Artists do almost all of the work themselves.  
The host should do almost nothing.**

Artists must be able to:

1. Open the public website.
2. Choose an available upcoming LIVE session.
3. Submit their artist information.
4. Submit their song information.
5. Write a short introduction for the host to read.
6. Provide their social links.
7. Provide a playable music link and/or upload an audio file when file storage is enabled.
8. Agree to the rights/permission statement.
9. Submit.
10. Automatically receive a position in the selected LIVE queue.

The host should later only have to:

1. Open the admin area.
2. Select the day/session.
3. See all registered artists in exact queue order.
4. Start LIVE Mode.
5. Read the artist information.
6. Press **PLAY**.
7. Press **MARK PLAYED / NEXT**.
8. Continue to the next artist.

The host must NOT manually copy submissions between systems.

The host must NOT manually create queue entries.

The host must NOT search through Telegram messages, emails, spreadsheets, or folders during the livestream.

Everything must work directly from this website.

---

# 2. MOST IMPORTANT UX PRINCIPLE

The application must prioritize simplicity for the HOST above everything else.

The admin is not supposed to operate a complex CRM.

During the livestream the host may be simultaneously:

- talking to TikTok viewers,
- reading comments,
- controlling audio,
- controlling OBS/TikTok LIVE Studio,
- introducing artists,
- monitoring the livestream.

Therefore LIVE Mode must require virtually no thinking.

Large controls.

Very little text clutter.

Very clear current track.

Very clear next track.

No unnecessary menus.

No confusing workflow.

No modal windows unless absolutely necessary.

The desired host experience is:

**Open → choose today's session → START LIVE MODE → PLAY → NEXT → PLAY → NEXT.**

# 3. LANGUAGES — CRITICAL REQUIREMENT

The entire public application MUST support three complete languages:

### English — EN
### French — FR
### Ukrainian — UA

A visible language selector must be available in the interface:

**EN | FR | UA**

The language selection should persist for the visitor using local storage or another appropriate method.

Every user-facing text string must use the localization system.

DO NOT hard-code English directly throughout components.

Create proper translation files/dictionaries, for example:

- `en`
- `fr`
- `uk`

or an equivalent i18n architecture.

This applies to:

- navigation
- titles
- subtitles
- buttons
- form labels
- placeholders
- validation messages
- success messages
- error messages
- LIVE session information
- availability labels
- queue messages
- legal/permission statements
- admin labels
- LIVE Mode
- status names
- empty states
- confirmation dialogs
- tooltips
